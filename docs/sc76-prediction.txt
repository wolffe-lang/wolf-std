sc76 prediction, before the first implementation or test change

P1. On trunk dee6206 the Linux RSS bound (1 GiB minus 64 MiB < 8 MiB) fails for update256 and update512: the 2 GiB address-space cap fires before 1 GiB. Measure 16 MiB, 64 MiB and 1 GiB, native and release, checked where its execution budget permits. Never run growing trunk code on macOS.
P2. Reuse state-owned message schedules, indexed only by public round number, and reset the block buffer in place. Allocate schedules once in constructors; compress/update and their per-block callees allocate nothing. The caller-ambient rule [mem.region.create.3] and wholesale-only reclamation [mem.region.intra.2] explain trunk's growth. Reuse avoids scratch escape [mem.region.escape], keeps every public function signature and ct comment true, and keeps wolf/lupin pins unchanged.
P3. After reuse, incremental RSS is independent of input length. One-shot measurements must separate caller input storage from hashing overhead: a 1 GiB materialized List[byte] necessarily occupies 1 GiB, so the literal total-process RSS delta is not a valid O(1) auxiliary-memory bound for sum256. Record that distinction explicitly rather than weaken the incremental bound.
P4. Existing SHA-2/FIPS/CAVP, HMAC/HKDF, Ed25519, TLS/PKI and other SHA-2 caller tests keep their ledger words and byte-identical digests. Checked long runs may hit the documented execution budget; unsupported is not green memory evidence. Pin 0.2.36 / 0.1.58 remains.
P5. A separate sc76-plant-schedule branch restoring one fresh SHA-256 schedule per block is red at the named bounded-memory row; it never lands on sc76. A small region-cap row exposes this in ordinary CI without a 1 GiB job on macOS; Linux RSS measurement remains the decisive long-stream bound.
