# sc81 — wolf-std: sessions and pseudo-terminals

Footprint: cross-cutting (the toolchain pins move: `vendor/tools.toml`, the `upstream` data pin and its snapshot, and `xtask`'s mirror-lag table)

wolf 0.2.39 adds a child started in a session of its own (`os_spawn_session`), this process moved into one (`os_setsid`) and read (`os_sid`), and a pseudo-terminal: the pair (`os_term_open_pty`), the slave's name (`os_term_pty_name`), the size with its pixels (`os_term_set_size`) and the settings by RFC 4254 opcode (`os_term_attr`, `os_term_set_attr`). This lane gives them a std surface, so that an ssh server can run each remote command in its own session and answer a terminal request by running a login shell on a pty, relaying bytes and window changes.

## Design

The order a server follows, which the surface is built around (`[os.term.pty]`):

1. `let p = term.open_pty()?` and `let name = term.pty_name(p.master)?`.
2. `term.set_size(p.master, term.Size { rows: r, columns: c }, xpx, ypx)?`, and `term.set_attr(p.master, op, value)` for each mode the client sent (an op the host lacks is `unsupported`, and the server passes over it as `sshd` does).
3. `let f = process.fork()?`. In the child: `process.lead_session()?`, then `var tty = term.open_controlling(name)?`, then the program with `tty` on 0, 1 and 2 (`set_stdin`, `set_stdout`, `set_stderr`) by `process.exec` (or the builtin `os_exec` with an environment). The inherited `p.master` and `p.slave` are close-on-exec, so the exec closes them; the child keeps its inherited slave until its own open, which keeps macOS's settings.
4. In the parent: `fs.close(take p.slave)?` after the fork; relay `p.master` with `signal.wait_fds`, `fs.read_chunk` and `fs.set_nonblock` plus `fs.write_some`; on each `window-change`, `term.set_size(p.master, …)`; close the master at the end.

A command without a terminal needs only step 3's first call: `process.lead_session()` in the fork's child, where burrowd calls `process.lead_group()` today. A program that spawns rather than forks calls `process.start_session(c, defaults)`; its child leads a session with no controlling terminal, and a slave placed in its map is a terminal on 0, 1 and 2 that is not its controlling terminal.

### Rulings, each with the option implemented

- **R-sc81-1, where it lives.** (A) The spec's own homes: `process.start_session`, `lead_session` and `own_session` beside `start_job`, `lead_group` and `own_group` (`[os.proc.session.note]` names the three), and the five pty calls in `std.term` beside `size`, `mode` and `chars` (`[os.term.pty.note]`: "wolf-std's `term` gains the five"). (B) A new `std.pty` module. (C) Options on the `Command` (`set_session`, `set_terminal`). **Recommended and implemented: A.** (C) fails twice: a session is a property of the spawn, not of the command (sc39's reasoning for the inherit set), and a "controlling terminal" option cannot be honoured by a spawn, since the map's placement never makes a terminal controlling and std runs no code in a spawned child between its `setsid` and its `exec`. (B) splits the terminal across two modules.
- **R-sc81-2, the session id's type.** (A) `own_session() -> int`. (B) A `Session { id }` struct, as `Group`. **Recommended and implemented: A.** No call takes a session id (there is no send to a session and no join), so a struct would carry nothing a caller can use; `Group` earns its type because `signal.send_group` takes one.
- **R-sc81-3, the pair.** (A) `Pty { master: fs.File, slave: fs.File }`, `process.Pipe`'s shape. (B) A tuple. (C) The master alone, with the slave reached by name. **Recommended and implemented: A.** The caller owns both ends; both are close-on-exec, so neither reaches a child except through a map; the parent closes its slave after the fork and its master at the end, and the doc on `Pty` says so in that order.
- **R-sc81-4, the controlling terminal.** (A) A std call for the child's step, `term.open_controlling(name)`: it refuses a name that is not a character device without opening it (so nothing is created), opens it read-write, and answers it only if it is now this process's controlling terminal (the terminal's foreground is this process's group), closing it and answering `io` otherwise. (B) Documentation only: the child writes `fs.open_mode(name, 3)`. (C) A composed `process.start_on_pty(c, p, defaults)` that forks inside std. **Recommended and implemented: A.** (B) fails silently: an open before `lead_session`, or a use of the inherited slave's descriptor, gives the child a terminal that is not its controlling one, and nothing says so until Ctrl-C or a window change reaches nobody; and mode 3 creates a regular file for a missing name. (C) hides a fork (its `busy` rule, the checked machine's `unsupported`) and leaves no room for what a server does between the fork and the exec (the account's ids, the home directory).
- **R-sc81-5, the size set.** (A) `set_size(tty, s: Size, xpixels, ypixels)`. (B) A new four-field struct. (C) Two pixel fields added to `Size`, which would refuse every `Size { rows, columns }` literal that exists. (D) Two calls, with and without the pixels. **Recommended and implemented: A.** The pair `size` reads is the pair it takes, and the pixels are written at every call, so a server cannot drop them by accident (`[os.term.pty.note]`: a server that drops them signals differently from `sshd`). How a change reaches the child: the host sends `SIGWINCH` (`signal.resize()`) to the terminal's foreground group whenever any of the four fields changes, and nothing for the same four; std adds nothing.
- **R-sc81-6, the settings.** (A) `attr(tty, op)` and `set_attr(tty, op, value)`, by RFC 4254 opcode as an `int`. (B) A named function per opcode (56). (C) A decoder for RFC 4254's encoded-modes string. (D) Leave both out. **Recommended and implemented: A.** A server reads (opcode, value) pairs off the wire and hands them on unchanged, so the published number is the vocabulary; (B) is 56 functions over a numbering that is already public, and (C) is the wire format's, which is the server's.
- **R-sc81-7, the relay.** (A) Nothing new: the master is an `fs.File`; `signal.wait_fds` waits on it to read (and with `WAIT_WRITE` to write), `fs.set_nonblock` with `fs.write_some` writes what it takes, `fs.read_chunk` and `fs.read_into` read what is there. (B) A pty reader that turns linux's `EIO` at the end into `eof`. (C) A task per direction. **Recommended and implemented: A,** with the end documented: after the child's last slave descriptor closes, a master read answers `io` on linux (the host's `EIO`, 5 in `os_error()`) and `eof` on macOS, and either ends the relay. (B) is a function whose only work is to rename one tag on one host.
- **R-sc81-8, errors and platforms.** Every row is the builtin's own tag, in the os tier's vocabulary (API-CONVENTIONS §14): nothing is coarsened or renamed. linux and macOS serve every call; PAX runs the static linux binary through its kernel's `setsid`, `/dev/ptmx`, `TIOCGPTN` and `TIOCSPTLCK` (the spec's statement; not measured here); windows answers `unsupported` by name for all of them; the checked machine serves them in the `wolf` process (so `lead_session` and `open_controlling` would move the `wolf` process there: the rows call `lead_session` only in a child, and `open_controlling` in a test's own process only where it must refuse); lupin answers the rows decided before a session or a terminal and refuses the rest by name. `open_controlling` decides the host first (`os_pgid`'s `unsupported`), then the name (`not_found`; `io` for one that is not a character device), then the open (`denied`, `io`), then the terminal (`io`, with the file closed).
- **R-sc81-9, out of scope.** A termios image, VMIN and VTIME by opcode (the `Mode`'s), job-control helpers past those that exist (`start_foreground`, `set_foreground`), login records (utmp), `TIOCNOTTY`, a `ttyname` for a slave, a composed run-on-a-pty spawn (R-sc81-4 C), a session type (R-sc81-2) and a pty reader (R-sc81-7 B). Each would be surface without a consumer that needs it.
- **R-sc81-10, the pins.** The new calls need wolf 0.2.39, so the binary pin moves to wolf 0.2.39 and lupin 0.1.61, and the data pin to `3fc86f77`, each its own commit. What the bump moves: the lupin cells lupin 0.1.59 to 0.1.61 advanced (wolf-std#125's seven, measured), each flipped in its own commit, and the two `std.os` mirror-lag entries retired in `xtask/src/doc_examples.rs`. That makes the change cross-cutting.

### The windows rig's time

The second labelled run at `89b6450` (run 43031208211) was cut at the windows rig's 90-minute cap twice, and trunk's nightly was cut the same way on 11-08 and 11-09, before this branch. Read from the hosted logs (each test line's timestamp, and the slowest-invocation tables):

- The windows rig job took 45.4 and 50.5 min on trunk at `b1babae` and `3111d39` (11-03, 11-05). At `d4a4d4c` (the public-PKI rows) the same job took 89.5, 68.6 and 89.3 min (11-05, 11-06, 11-07); at `2411d86` (scrypt and passwd) 85.6 min green on 11-10.
- Against 11-05's 49.7 min of `std-test`, 11-07's 88.4 min holds `x/crypto/rsa` (11.0 min) and `x/crypto/p384` (10.9 min) that were not there, and `x/tls/cert` grew 3.1 min. Each of those rows costs about 37 s on windows, nearly all of it lupin running into its step budget before it declines; the slowest-invocation tables are lupin's crypto rows, 50 to 97 s each.
- The same rows on another runner differ by about 30%: `x/crypto/curve25519` took 20.8 and 27.2 min, and the commit `d4a4d4c` ran 68.6 and 89.5 min whole. This branch's first labelled run took 72.2 min there; sc81's thirteen rows cost 6 s of it.

So the cap moves instead: 120 min for the windows leg (1.34 times the slowest whole job seen, 89.5 min), ubuntu and macOS unchanged at 90 (`b1845cf`).

### What the rows showed on Linux

- A fork's child leads no group, so `lead_session` is served there and `denied` the second time; a child of `start_session` already leads one, so its `lead_session` is `denied`.
- From outside, a session of its own is told by the join: a spawn into a group of another session is `denied`, into one of this session served.
- A pty slave in a spawn's map is a terminal on 0, 1 and 2 but not a controlling one (`/dev/tty` fails), and with no session holding it, the master's close sends nothing: the shell's next read ends instead. Taken by name after `lead_session`, it is controlling: `/dev/tty` opens, a size change signals the foreground, 0x03 interrupts it.
- A change of the pixels alone signals; the same four fields do not.
- With the slave's last descriptor closed, the master's read is `io` on linux.
