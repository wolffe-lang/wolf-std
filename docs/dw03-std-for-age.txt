dw03 — Standard-library prerequisites for age v1

Forbidden

No new cryptographic construction, generator, cipher, recipient scheme or key
format. Only the published age v1 specification, RFCs 7748, 5869, 2104, 4231,
8439 and 4648, BIP-173, published vector data, and this library's own sources
and tests are inputs. No external cryptographic implementation source was
read. No changes to poll or net. No change to existing public signatures,
semantics or security guarantees without approval beyond the two codecs and
random-byte surface expressly requested.

Prediction

Written before implementation. The RFC-vector outputs should not change.
The selected one-call HKDF path produces a 32-byte PRK before expansion;
HMAC's long-key reduction is already present. AEAD open already authenticates
before calling stream_xor. The initial confirmed source changes needed are
the X25519 zero check and the secrecy/timing documentation, not a replacement
cipher or ladder.

Expect a source-behavior inspection to reject is_zero_bytes: its per-byte if
reads the shared secret. Replace it with an unconditional OR fold only after
a committed red inspection row. Preserve the zero error and all RFC outputs.
Test each nonzero-byte position and the all-zero input; the behavior row must
also inspect executed control flow or generated code, since output equality
alone cannot detect a branchy comparison. Source shape is not a timing proof.

For AEAD, add rejection at every tag position using the published RFC 8439
box, AAD/ciphertext mutation, empty plaintext, and every box length below 16.
Assert the tag row and no returned plaintext. Separately inspect that the
failure edge precedes decryption; a black-box rejection row cannot prove that
plaintext was never computed internally. Preserve the published A.5 answer.

For X25519, retain RFC 7748 section 5.2, section 6.1 and chain rows; add named
rows for top-bit masking, scalar-clamp equivalence and all 19 noncanonical
u-coordinates reduced modulo p, preserving the zero refusal. Full native
Wycheproof/chain evidence is separate from checked/lupin smoke evidence.

For base64, add encode_raw/decode_raw beside the padded pair; never change
decode or use the lenient/URL profile. RFC 4648 section 10 vectors with the
age-specified omitted padding must pass. Padding, whitespace, URL characters,
non-ASCII, a one-character tail, and nonzero residual bits must return parse.
Keep parsing linear and avoid repeatedly copying the unconsumed input.

For Bech32, use the BIP-173 checksum, not Bech32m. Test its generic valid and
invalid checksum strings, mixed case, invalid HRPs and characters. Pin the
published age X25519 recipient and labelled test identity examples, exact
32-byte decoded length, and zero/short conversion padding. The age document
removes the data-part length limit; do not accidentally promise every age
recipient profile from the two classical key examples. No secret input in an
error or diagnostic. These encoders are not assumed fixed-time.

For random bytes, expect no production fallback, deterministic seed or weak
source. Linux uses initialized getrandom(flags=0); macOS uses getentropy in
at most 256-byte calls. Short progress and EINTR belong at the OS adapter;
zero progress and provider failure cannot be success. Keep the pending PAX
adapter behind one function and refuse until its exact contract is available.
The pinned os_random contract is trapping, so the named-error requirement
needs an upstream contract decision before an implementation can be honest.

Source citations and quoted gaps:

* std/x/crypto/curve25519/curve25519.lu:914-915 says "the reject-on-zero
  test is on the PUBLIC output." Lines 943-951 repeat "public output"
  and implement `if !(v as int == 0)` inside the byte loop. This is secret
  material: the only intentional disclosure is the final all-zero verdict,
  not the pattern of zero bytes. RFC 7748 section 6.1 describes an OR of all
  bytes; section 5.1 separately warns that fixed field-operation sequences
  do not eliminate all side channels. This finding is from the function's
  source; no machine-timing exploit has been measured.
* The curve module header at lines 7-10 says both curves "are constant-time
  by construction in portable code"; its signing path is explicitly outside
  this audit. X25519's arithmetic cswap is fixed-looking source, not a
  machine-code certificate. Checked arithmetic, runtime representation,
  division instructions and optimizer behavior still require pinned review.
* std/x/crypto/chacha20/chacha20.lu:7-8 says its "constant-time story is true
  by construction in portable code"; lines 93-101 conclude there is "no
  value-dependent branch anywhere". Source control flow does not warrant a
  claim about all generated instructions or all execution tiers. The native
  default/release binaries and checked/lupin runtimes have not been reviewed
  here. The source of open at lines 792-819 does verify before decryption;
  that is narrower than an assertion of no possible plaintext leakage.
* tests/x/crypto/chacha20/flipped_tag_row.lu mutates the last tag byte of
  the RFC 8439 section 2.8.2 example and asserts an empty fallback; the
  truncated_box_row also observes the tag row. Neither proves no internal
  plaintext computation, no residual copies, or full-stream completeness.
* std/x/crypto/sha2/sha2.lu:982-984 says PRK "must be at least one block's
  worth of entropy per the RFC". RFC 5869 section 2.3 says "a pseudorandom
  key of at least HashLen octets", normally Extract's output: 32 bytes for
  SHA-256, not the 64-byte compression block, and not a claim that an API
  can inspect entropy. The one-call age path always produces 32 bytes.
  The standalone expand path constructs pads directly rather than invoking
  hmac256's long-key reduction, so PRKs longer than 64 bytes warrant a
  separate issue/test outside the selected age path; no such behavior was
  measured or changed by this lane.
* std/base64/base64.lu:24-31 distinguishes strict padded decode from the
  lenient and URL variants. None is strict unpadded standard base64. Raw
  encoding/decoding is to live in this module, not in a downstream copy.
  Bech32 is absent. Its generic checks and byte conversion must remain
  separate: a valid checksum does not guarantee canonical 32-byte key data.

Random-byte contract blocker

The public specification at the pinned wolf commit, spec/11-os.md section 2,
provides os_random(int) -> List[int]. Its platform contract is Linux
getrandom(flags=0), continuing short reads and EINTR; macOS getentropy in
256-byte chunks. These are specification statements, not a new inspection
of runtime or OS implementation code. std.rand itself remains seeded PCG32
and explicitly says "It is NOT cryptographically secure" (lines 21-23).

[os.random.trap] states: "Failure is a TRAP, never a silent fallback" and
"There is deliberately NO error row on this surface". [os.random.sole]
requires every cryptographic byte source to bottom out in os_random. The
trap is assert and is not catchable as an error row (API-CONVENTIONS section
13; spec/05 [conf.trap.exit]). A std wrapper can narrow the successful
List[int] to List[byte], but cannot turn unavailable/unqualified readiness
into distinct named errors. Testing success or prechecking a platform name
cannot repair this loss of information. Calling a device or foreign function
instead would evade [os.random.sole], and would not settle PAX readiness.

Approval required, not implemented:
A. Add an upstream recoverable sibling primitive, preserving os_random's
   existing trapping behavior. Its approved contract distinguishes invalid
   request, unqualified provider and unavailable provider, guarantees all-or-
   error delivery, and forbids fallback. std wraps it as byte values and
   keeps one PAX adapter pending the final kernel ABI. Recommended.
B. Change os_random itself to return rows. This changes a ruled language
   surface and existing callers; require a separate compatibility decision.
C. Keep the trapping builtin and weaken the requested std surface. This
   does not meet the named-error acceptance gate; not recommended.

Do not emulate recovery by catching a proc fault or translating every assert
into entropy_unavailable: allocation, programming errors and provider failure
would be conflated, and provider qualification still could not be observed.
Until the approved PAX call exists, a PAX adapter must refuse
entropy_unqualified without trying its legacy successful random-byte path.
No guessed flag, device, capability filename or errno is proposed here.

Shared comparison and claim approval required

std.x.tls.handshake.ct_eq already exists publicly (lines 635-656). It returns
false for unequal public lengths and unconditionally folds XOR differences
for equal lengths. This corrects the earlier assumption that no public helper
exists. Do not create a second implementation merely because its current
home is inconvenient.

A. Add one shared pure byte comparison, provisionally
   bytes.is_equal_fixed_work(a, b), and route the selected AEAD path and
   future age header MAC through it, preserving TLS's existing public entry
   if that entry is later delegated in its own scoped change. This adds a
   public API beyond the two codecs and random surface. Recommended only
   after approval. Document equal/public lengths, every-byte accumulation,
   and the fact that source fixed work is not universal constant time.
B. Keep the existing public ct_eq and couple age/AEAD to a TLS handshake
   module. No new public function, but an unrelated nursery dependency and
   larger review/import surface. Not recommended.
C. Duplicate private comparison loops in consumers. Small immediate diff,
   but multiple owners and no single selected-path obligation. Not recommended.

Proposed claim boundary for approval: a source-level no-early-exit byte fold,
with behavior rows and separately identified default/release generated-code
observations at exact pins. No universal fixed-time guarantee, no timing
certificate for lupin or checked execution, and no claim that arithmetic
operation counts prove instruction latency or secret erasure. Existing
security overclaims should be reduced, not replaced with another guarantee.

Where the age codec should live

A std module would let multiple tools share one format implementation, but
requires a new public streaming/error/resource API and a resolution of the
nursery dependencies. Its independent reviewer must read the std revision
plus compiler/runtime pins; a std release and consumer pin bump accompany
format fixes. Neither nursery status nor std's gates replaces that reading.

An internal denward module keeps the format and its resource-admission API
next to the only current consumer, without expanding std or graduating its
crypto residents. Generic text codecs and random-byte adaptation remain std's
single-owned reusable parts. denward pins the reviewed std/compiler/runtime
set, and its independent reviewer reads both that exact set and the complete
format implementation. A later second consumer can motivate extraction by a
separate surface decision. Recommend the internal denward module, conditional
on approval; no format implementation was written here.
The draft is docs/dw03-draft-dw04-age.txt. Both locations still require the
same independent hostile-input and interoperability evidence before use.
