## 2026-08-30 (sc29) — the client shakes the hand; the tests are the server

- A HALF of a tier can land one release behind its other half, and the
  proof it is a GAP not a decline is the sibling that works. s106 shipped
  the net byte tier AND `net_deadline`; lupin 0.1.18 resolves the str
  reads/writes and arms the deadline (both measured three-lane at the pin
  — a 150ms `set_deadline` budget resolves a silent-peer read as
  `timeout` under lupin), but `net_read_bytes`/`net_write_bytes` are
  `unsupported` at resolve there (F-0102). The working str tier is what
  makes the byte tier's refusal a completeness bug rather than a design
  decline — the fix's shape is the str calls' own — and it is why the
  sc29 client's SOCKET witnesses are compiler-lanes-only while its PURE
  parse/verify half stays three-lane by lupin's lazy body resolution.
  When one call of a family refuses, probe its siblings before writing
  "the lane lacks the tier": the family may be half-crossed.

- A TAG declared for years against a day that had not come is paid in
  full the moment its builtin lands, with no signature change — which is
  the whole point of declaring it early. `std.net`'s `timeout` was
  vocabulary-only from sc08 (F-0049: a runtime deadline no builtin
  armed); s106's `net_deadline` closed it and sc29's `set_deadline` /
  `set_listener_deadline` wrap it on all three lanes. Not one row moved,
  not one caller broke — the tag every read and accept already carried
  simply became reachable. The lesson for a surface with a known hole:
  declare the row against the fix from day one and the fix is a pure
  addition; a row retrofitted later is a breaking change to every handler.

- A single-threaded, no-reactor language can still test an in-process
  client against an in-process server, if the protocol is driven in
  PHASES that alternate with kernel-buffered flights. Every net op blocks
  the whole process (no `select`, no tasks at this tier), so a client
  that reads while a server reads deadlocks. The sc29 client splits
  `begin` (write ClientHello, return WITHOUT reading) from `complete`
  (read the flight, write the client Finished): the test's server half
  runs BETWEEN them, reading the buffered ClientHello and writing its
  whole flight into the loopback buffer before `complete` ever reads.
  Strict alternation, every read served from a buffer a prior write
  filled — the dial-first net discipline (sc08) generalized to a whole
  handshake. The two-process alternative (`std.process`) costs a spawned
  binary no lane here builds; phase separation costs one extra call and
  keeps the witness single-file and three-lane-shaped. Record the shape
  you chose and why, in the module header — it is an API decision, not a
  test trick.

- "The tests are the server" is a DIFFERENTIAL turned inward, and it
  proves more than a vector file can. The sc29 client's flagship shakes a
  full TLS 1.3 handshake against a server half built from the SAME
  library primitives it parses — sc21's message/schedule builders, sc20's
  `record.seal`, sc18's `curve25519.sign` — so a bug in the client's
  parser and a matching bug in the shared builder cannot agree by
  construction (lobo's fixture-CA lesson, the two halves of one library
  proving each other). And the certificate is REAL: the sc22 test PKI's
  leaf carries an Ed25519 SPKI that is `public_key(sha256("…leaf seed"))`,
  so the test signs a genuine CertificateVerify with the leaf's own
  deterministic key and the client verifies it against the SPKI the chain
  validated. Reuse the vendored corpus as a live oracle, not just as
  parse fodder — a deterministic key you can re-derive is a signer.

- The CertificateVerify RETIREMENT is a DISPATCH, and each arm names its
  answer so the honesty split cannot rot into a silent accept. sc21 built
  the §4.4.3 octets and verified nothing; sc29 retires that for exactly
  the two schemes the ladder can verify — ed25519 via `curve25519.verify`,
  ecdsa_secp256r1_sha256 via `p256.verify_der` — and every other scheme,
  rsa_pss included, is the NAMED `unsupported_alg` ROW, never a bool a
  caller can forget (§2). A recognized scheme whose signature does not
  check is `bad_signature`; a recognized scheme over the wrong key type is
  `bad_signature` too (that key could not have produced it). Return an int
  through the row (1 on success), never a bool: a verify that answers
  `false` invites the caller to treat "unsupported" and "forged" the same,
  and the whole load-bearing post of this rung is that they are different.

- Every adversarial input is a NAMED row and the battery is PURE, which
  is what keeps it three-lane and fast. The sc29 negative battery
  (wrong-name, expired, downgrade, HelloRetryRequest, wrong
  suite/group/version/compression, truncated ServerHello, tampered
  record, bad Finished, bad CertificateVerify signature) touches no
  socket: each refusal is `parse_server_hello` / `check_negotiation` /
  `record.open` / `accept_finished` / `validate_chain` /
  `verify_certificate_verify` answering its tag over a hand-built or
  one-byte-mutated input. A parser that never traps on wire data (§10:
  data raises where a caller's mistake traps) is the precondition — every
  index window-checked, every reject a `decode_error` — and it is what
  lets the negative cases be ordinary values a `match` names rather than a
  process the rig has to catch. Build the reject surface so the battery is
  a pure function of its input; the socket is for the POSITIVE witness
  only.

- Hold a descriptor as an `int`, not a `net.Socket`, in any struct whose
  methods take `mut self` — F-0092 (the native rung refuses
  `f(mut param.field)` when the base is itself a `mut` parameter) makes
  `net.read_bytes(mut c.sock, …)` inside `read(mut c: Client)` a native
  refusal. The portable shape: an `int fd` field (a field read is a copy),
  rebuild the one-field `net.Socket { fd: … }` wrapper at each call (the
  sc08 forge rule makes that ordinary code), and `take` the struct in the
  closer so staleness stays a static use-after-move. The wrapper type is
  a value you reconstruct, not a handle you store.
