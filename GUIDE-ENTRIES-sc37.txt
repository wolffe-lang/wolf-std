## 2026-09-06 (sc37) — the red that proves the green, and the words a calendar owes

- RUN THE GAUNTLET BEFORE YOU FIX THE THING THE GAUNTLET IS SUPPOSED TO
  CATCH. This sprint's first item was ten ledger rows that had gone
  stale under a new interpreter release. The rows were known, the issue
  named eight of them, and the fix was mechanical — which is exactly the
  situation in which a lane edits first and measures after, and reports
  a green that proves nothing. The order was inverted on purpose:
  install, measure, WATCH IT GO RED, then edit. The red is the evidence;
  the green afterwards is just confirmation that the edit matched it. If
  you cannot show the red, you have not shown that the ledger was doing
  its job — you have shown that you and the ledger agree, which is a
  much weaker claim and the one a stale ledger also satisfies.

- THE RED CAUGHT TWO ROWS THE PREDICTION MISSED, AND THAT IS THE WHOLE
  ARGUMENT FOR THE ORDER. The prediction, written before measuring,
  named eight rows and explicitly reasoned that two others would NOT
  move: the release notes described a change of MECHANISM in them (a
  refusal now arriving before an unrelated decline), not a change of
  observed word. Ten rows went red. A program refused earlier never
  reaches the tier that was declining it, so the mechanism change WAS a
  word change. Predict in writing — it is what makes a miss legible —
  but let the runner have the last word, and write the miss down next to
  the hit. A prediction file that only ever records successes is a file
  nobody is learning from.

- VERIFY THE MACHINE, EVEN WHEN — ESPECIALLY WHEN — YOU ARE TOLD NOT TO
  BOTHER. The instruction was "the machine already runs X and Y; verify
  and record, don't rebuild what is already correct". One of the two was
  three days stale. The tracking issue had it right where the
  instruction had it wrong, and a lane that had accepted the premise
  would have run its whole gauntlet against the old binary, seen green,
  and closed the issue as needing no work. `--version` costs a second.
  The clause that says "verify" is load-bearing even when the clause
  next to it says "already".

- PROBE THE LANE THE RIG ACTUALLY RUNS, NOT THE ONE WHOSE FLAG LOOKS
  RIGHT. Two calls were measured with `wolf run --checked`, answered in
  a way that flatly contradicted the specification, and were one step
  from being filed upstream as a divergence. `wolf run --checked` runs
  the NATIVE build; the checked machine answers through `conform-run
  --checked`, and under it the specification was correct in every
  particular. Before you file a finding against a document, confirm the
  binary you measured is the binary the document is about. A false heal
  and a false defect are the same error wearing different signs.

- SOME LANE WORDS ARE OWED TO A CALENDAR, AND THEY MUST SAY SO. A
  builtin can land in a compiler release that the reference interpreter's
  newest release does not yet conform to. The interpreter then does not
  DECLINE your call — it has never been shown it. That is not a
  divergence (divergence means the machines disagree about what a
  program MEANS) and it is not a defect worth filing; it is release
  ordering, and it retires on a date rather than on a fix. Give it a
  finding name, say which two pins it sits between, and make sure
  retiring it costs a ledger word and not a rewrite.

- WHEN TWO HOSTS BOTH SERVE A FEATURE AND BEHAVE DIFFERENTLY, PROMISE
  THE INTERSECTION AND DOCUMENT THE DIFFERENCE. The easy case is when
  hosts return different error tags: the vocabulary shows the seam. The
  harder case is when both succeed and differ in DEGREE — here, one
  kernel distributes accepted connections across a group of listeners
  and the other hands every one to the newest. No row can express that.
  So state both postures by name in the doc, work out what both hosts
  actually guarantee, promise exactly that, and write the witness to
  assert the guarantees and NOTHING about which host you are on. The
  test that encodes your laptop's kernel policy is the test that fails
  on the other tier-1 platform six weeks later.

- A WITNESS SHOULD SAY WHAT IT CANNOT REACH INSTEAD OF FAKING IT. One
  call this sprint is the CHILD's half of descriptor inheritance: the
  numbers it exists for are handed across a spawn, and the harness runs
  one program per test with no parent. Rather than construct a fake
  parent, the witness measures every REFUSAL — which is the half a
  program actually has to survive — and its header states plainly which
  case is unreachable and why. An honest gap that a reader can see beats
  an elaborate fixture that tests the fixture.

- EVIDENCE THAT MATTERS BELONGS IN A COMMIT, NOT IN /tmp. This lane
  wrote its predictions to a shared scratch directory before measuring,
  which is the right discipline in the wrong place: a concurrent lane
  pruned that directory mid-sprint and took the prediction file and a
  running job's log with it. The prediction survived only because it
  could be reconstructed and quoted into the findings document. If a
  piece of evidence is load-bearing for a claim you are going to
  publish, put it where the repository's history will keep it.
